# 함끼 · AI 기능 설명

- 서비스: 함끼(Hamkki) — AI가 고르고, 함께 정하는 한 끼
- 배포 URL: https://hamkki.onrender.com
- GitHub: https://github.com/EOBG-eg/hamkki

## 1. Gemini로 처리한 일

사용자가 입력한 **상황**(데이트·가족·친구·회식·혼밥), 인원, 시간대, 예산, 그리고 **자유 문장으로 적은 분위기 요청**
(예: "부모님 모시고 조용히", "오랜만에 만나서 얘기 많이 할 곳")을 해석해서,
서버가 추린 근처 식당 후보 20곳 중 **가장 어울리는 3곳을 고르고 추천 이유를 한두 문장으로 작성**한다.

추천을 본 뒤 "더 저렴한 곳으로", "조용히 얘기하기 좋은 곳"처럼 **조건을 문장으로 덧붙이면**(최대 3번)
처음 조건과 덧붙인 요청을 함께 반영해 다시 고른다. 이때 이미 보여준 식당은 다시 고르지 않는다.

| 역할 | 담당 |
|---|---|
| 장소 검색, 반경 1km 식당 찾기, 음식 종류 필터, 상황에 안 맞는 업종 제외 → 후보 20곳 | 서버 (정해진 규칙) |
| 분위기 문장·덧붙인 요청 해석 → 3곳 선택 + 추천 이유 + 한 줄 요약 | **Gemini** |
| AI가 고른 식당이 실제 후보인지 검사, 실패 시 대체 화면 | 서버 |

## 2. 왜 AI가 필요한 기능인가 (if문·SQL로 안 되는 이유)

- "조용히 얘기하기 좋은 곳", "부모님이 편하게 드실 곳" 같은 문장은 **사람마다 표현이 다르고 경우의 수가 끝이 없다.**
  키워드를 if문으로 나열하면 "시끄럽지 않은", "대화하기 편한", "차분한"처럼 같은 뜻의 다른 표현을 놓친다.
- 카카오 데이터에는 분위기·가격 정보가 없고 **식당 이름과 업종(예: 한식 > 국밥, 양식 > 파스타)만 있다.**
  "회식인데 다음 날 해장도 생각해서" 같은 요청에 맞는 곳을 고르려면 이름과 업종으로부터 어울림을 **추론**해야 한다.
- 결과에는 "왜 이곳인지" **사용자의 상황에 맞춘 설명**이 필요하다. 고정 문구로는 상황마다 다른 이유를 쓸 수 없다.
- 재추천은 "아까보다 더 가까운 곳 + 처음 조건도 유지"처럼 **대화의 흐름**을 이해해야 한다.

반대로 거리 계산, 음식 종류 필터처럼 **규칙으로 정확히 되는 일은 AI에게 맡기지 않았다.** (빠르고, 틀리지 않고, 쿼터를 아낌)

## 3. AI를 믿을 수 있게 만든 장치

1. **없는 식당을 지어내지 못하게** — AI에게는 서버가 고른 후보 목록(ID 포함)만 주고, 돌아온 ID가 실제 후보인지 서버가 다시 검사한다. 후보 밖이면 버린다.
2. **모르는 것을 단정하지 않게** — 프롬프트에 "가격·영업시간·실제 분위기 정보는 없으니 '~일 가능성이 높아요'처럼 추정으로 표현"하도록 규칙을 넣었다.
3. **AI가 실패해도 서비스는 동작** — 응답이 늦거나(모델당 20초, 전체 40초 제한) 쿼터 초과·형식 오류가 나면 후보 목록을 대신 보여준다. 모델 3개를 차례로 시도한다.
4. **재추천에서 같은 식당 반복 방지** — 프롬프트로만 막지 않고, 이미 보여준 식당을 서버가 후보에서 아예 뺀다.
5. **무료 쿼터 보호** — 한 사람당 10분 6회, 하루 전체 300회로 제한해 데모 중 AI가 멈추지 않게 했다.

## 4. 사용 모델·패키지

- 패키지: `google-genai`
- 모델: `gemini-3.5-flash-lite` (실패 시 `gemini-3.8-flash` → `gemini-3.6-flash`)
- 응답 형식: JSON (`{"summary": ..., "picks": [{"id": ..., "reason": ...}]}`)
